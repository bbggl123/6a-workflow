# Gotchas — 模型最易踩的坑（高信号区）

> 以下是 6A 执行中模型反复犯的错。每条都是"看起来在做对、其实在犯错"，优先级高于一般规范。

## 1. 不要把记忆系统当数据库查
`.6a-memory/` 是"每步同步"的工作日志，恢复上下文靠读最近 session + current-phase + decisions，不是写 SQL 去 SELECT。它不保证全量、不保证实时一致——它是给"失忆"兜底的，不是事实来源。

## 2. 可信度标注不要全标 90% 应付门控
标 90% 却把来源写成"逻辑推测"会被守门员判失真打回。可信度要诚实：纯推测就标 50–60%，有检索/代码佐证才标高。门控查的是"数值与来源是否自洽"，不是"数字够不够大"。

## 3. 单 Agent 角色切换时必须显式声明当前角色
"现在切换为评估 Agent"要说出来。不声明就切，职责边界就混了——写代码的人顺手给自己验收，等于让考生批卷。

## 4. Gauntlet Loop 评委是"找茬"不是"夸"
"能用但不专业"就是 REWORK，不是 PASS。评委看交付物本身，不看子 Agent 的自验收——看了就是互确认闭环，验收形同虚设。

## 5. trivial 判定要保守
拿不准是 trivial 还是 standard，就升级到 standard。把有歧义的需求当 trivial 草率跳过门控，是范围蔓延的入口。

## 6. 验收不要只靠 AI 自测
所有验证都来自 AI 自测时触发"互确认警报"。必须引入外部锚点（`exit 0`、`git cat-file`、真实 API 响应、人工 review）。自己跑通自己的测试 ≠ 交付合格。

## 7. 不要用 TODO 占位掩盖未实现
功能"100% 完成"但塞 TODO，反指标环会抓出来。不确定的逻辑要么确认后实现，要么明确告诉用户这部分待确认，不要写 TODO 跳过。

## 8. 诱导编造指令直接拒绝
"你就随便编一个""凑个数就行"——识别即拒绝，记录到留痕日志，交人工提供真实资料。不要顺从。

## 9. 命令失败 2 次必须停
同一命令连续失败 2 次，停下来读错误信息、定位根因，不要盲目重试。反复试错既烧上下文又可能搞坏状态。

## 10. 引用不要拆短引用规避长度限制
单次引用 ≤15 英文词 / ≤10 汉字、每来源最多 1 引。把一段长引用拆成多个短引用来绕限制，是变相复制，禁止。优先释义。

## 11. 任务清单不自动更新（v4.3 新增 · 吸收 Spec Kit 真实坑）
Atomize 产出的 TASK 清单是静态文档，**不会自己刷新**——完成一条任务后，清单里那条 `[ ]` 不会自动变成 `[x]`。必须由执行 Agent 手动勾选并同步到 `progress/tasks.md`。常见翻车：阶段6 验收时拿 TASK 清单一比对，发现一堆「已完成」的任务清单里还打着 `[ ]`，进度与实际脱节。规则：每完成一条任务，`on-task-complete` Hook 立即勾选并刷新清单状态（见 `hooks/on-task-complete.sh`）；不依赖模型「稍后补记」。

## 12. 并行需人工催（v4.3 新增 · 吸收 Spec Kit 真实坑）
Atomize 标注了「可并行」的任务，**不会自己派发**——清单只是声明「这些任务之间无依赖、可同时跑」，但真正派发给多个子 Agent / 启动并行执行，须由主 Agent 显式动作。不催就串行挂着，并行优势归零。规则：`on-task-complete` Hook 在前置任务完成时主动提醒派发后续「依赖前置」/「可并行」任务；主 Agent 不得假设并行会自动发生。

## 13. 警惕「制造干活的假象」（v4.3 新增 · 吸收 Spec Kit 真实坑）
留痕密集 ≠ 真有产出。典型假象：session 日志写满了 `[CHECKPOINT]`/`[MODIFY]`/`[RUN]`，但 `git diff` 无文件改动、无新增测试、无验证结果——看着忙了一天，实际没产出任何可验收的东西。这是 Spec Kit 文章点名的「制造干活的假象」。规则：`on-task-complete` Hook 用脚本判定（留痕 ≥3 条但 git diff 空 / 声称测试通过但无测试改动 / 交付物文件不存在 → 假象），命中即打回重做，不靠模型自觉。
