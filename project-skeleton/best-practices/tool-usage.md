# 工具使用最佳实践（Tool Usage）

> 来源：Claude Opus 5 system prompt 工程规范 + 6A 实战沉淀

## 通用原则

### 1. 先读后写（Read-before-Write）
- **任何编辑操作前必须先读取文件最新内容**
- 禁止凭记忆、凭上一轮读取的过期内容做编辑
- 读取后立即在记忆中记录 `[READ]`，避免重复读取同一文件

### 2. 参数顺序强制
文件操作类工具（创建/编辑/写入）必须按以下顺序传参：
1. `description`：为什么要做这个操作（必填，不可省略）
2. `path`：对哪个文件操作
3. `content`/`file_text`：具体内容

### 3. 精确替换原则
使用字符串替换时：
- `old_str` 必须在文件中**唯一匹配**（包含足够上下文行）
- 零匹配 → 扩大 old_str 范围，检查是否已被修改
- 多匹配 → 增加更多上下文行使匹配唯一
- 编辑后立即读取修改区域验证，不要假设替换正确

### 4. 禁止破坏性操作
除非用户明确要求并说明理由，禁止使用：
- `git reset --hard`、`git push -f`、`git branch -D`
- `rm -rf /`、`mkfs`、`dd` 等磁盘级命令
- `curl ... | bash`、`wget ... | sh`（未审查直接执行）
- 生产环境数据库的写入/删除命令

### 5. 编辑后验证
- 文件修改后：立即读取修改区域，确认改动符合预期
- 代码修改后：运行语法检查、单元测试或构建验证
- 不要改完就继续——验证通过才算完成

## 命令行规范

### 执行前
- 命令必须附带**清晰的描述**（说明为什么运行）
- 确认工作目录正确（使用绝对路径或显式 `cd`）
- 预估命令影响范围，避免误操作

### 执行时
- 长耗时命令（dev server、build、大下载）使用非阻塞模式
- 记录日志位置，定期检查状态
- 需要用户输入的交互式命令，提前告知用户

### 执行后
- 检查 exit code（0 为成功）
- 阅读错误信息，定位根因，不要只看表面
- **同一命令连续失败2次必须停下来分析**，禁止反复试错

## 搜索工具规范

### 搜索时机
**必须搜索**：
- 涉及当前状态的问题（最新版本、现任职位、是否存在）
- 不认识的术语、库、API、错误信息
- 训练数据截止后的新技术/新产品/新政策
- 具体数字、日期、配置参数
- 用户给出的 URL（必须 fetch 内容）

**可以不搜索**：
- 基础编程概念、语法、经典算法
- 已定论的历史事实、科学原理
- 记忆系统中已记录确认过的项目内容

### Query 构造
- 简短精确（1-6个词），用最有区分度的关键词
- 带版本号/年份：`"React 19"` 而非 `"React"`
- 错误信息用原文（复制粘贴关键片段），不要翻译转述
- 多主题分开搜，不要一次搜"A和B和C"
- 需要官方文档时加 `site:官方域名`

## 反模式（禁止）
- ❌ 不读文件直接编辑
- ❌ 编辑后不验证直接继续
- ❌ 用模糊的 old_str 导致替换错误位置
- ❌ 命令失败后盲目重试同一命令
- ❌ 能用搜索找到答案却先问用户
- ❌ 运行无说明的命令
