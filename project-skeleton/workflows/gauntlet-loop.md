# Gauntlet Loop —— 对抗式并行执行模式（v4.1 新增）

> 核心原理：主 Agent 拆解 → 子 Agent 并行执行 → 独立评委盲测验收 → 不达标自动打回循环。
> 适用：模块边界清晰、平台支持子 Agent 分发的 complex 任务（见 6A.md 第二章 triage 与第九章）。
> 本文件是 6A 阶段5 的**并行变体**，不取代六阶段骨架——阶段1–4、阶段6 照常走。

---

## 一、三段式结构

### Stage 1：主 Agent — 拆解 & 编排（= 规划 Agent，阶段1–4）

```
你是一个架构 Agent，负责将一个复杂编程任务拆解为可并行执行的独立子任务。

任务描述：{{TASK_DESCRIPTION}}
技术栈约束：{{TECH_STACK}}
交付标准：{{DELIVERY_CRITERIA}}

请按以下格式输出拆解方案：

【功能拆解】
列出所有需要实现的独立模块，每个模块：
- 模块编号：M1, M2, M3...
- 模块名称：一句话描述
- 核心职责：3 行内说明这个模块做什么
- 输入输出：这个模块接收什么，产出什么
- 依赖关系：依赖哪些其他模块（如有）
- 验收标准：5 条以内的硬性检查项

【并行分组】
将模块按依赖关系分组：
- Group A（无依赖，可最先执行）：M1, M3
- Group B（依赖 Group A）：M2
- Group C（依赖 Group B）：M4, M5

【技术约束】
- 每个子 Agent 只负责自己的模块
- 模块间接口定义清晰（JSON Schema / 函数签名 / API 规范）
- 所有输出必须可直接合并，无命名冲突
- 技术栈严格遵循：{{TECH_STACK}}
```

> 拆解方案须经**阶段4 Approve 人工确认**后才能分发给子 Agent。

### Stage 2：子 Agent — 并行执行（= 执行 Agent × N）

每个子 Agent 收到以下指令：

```
你是模块 M{{ID}} 的执行 Agent。

【你的模块】
名称：{{MODULE_NAME}}
职责：{{MODULE_DESCRIPTION}}
输入：{{INPUT_SPEC}}
输出：{{OUTPUT_SPEC}}
依赖：{{DEPENDENCIES}}

【执行要求】
1. 先输出你的实现计划（5 步以内），再写代码
2. 代码必须完整、可运行，不包含 TODO 或占位符
3. 严格遵循技术栈：{{TECH_STACK}}
4. 模块间接口必须与拆解文档完全一致
5. 不修改其他模块的代码，不引入全局命名冲突

【输出格式】
- 实现计划
- 完整代码（标注清楚文件路径）
- 自验收结果（对照验收标准逐条说明）
```

**6A 约束叠加**：
- 涉及外部依赖 / 未验证库版本 / 性能预估时，附四行可信度标注（6A.md 4.2）。
- 每修改一个文件、运行一次命令，立即同步到 `.6a-memory/session/`（`[MODIFY]`/`[RUN]`）。
- 多子 Agent 共享分支时守「消失即停」（6A.md 7.8），绝不 `reset --hard`/`push -f`。

### Stage 3：评委 Agent — 盲测验收（= 评估 Agent 独立盲测变体）

```
你是一个极其苛刻的代码验收 Agent（QA / 评委）。
你只关心一件事：代码是否达到了 {{DELIVERY_CRITERIA}} 标准。

【验收清单 — 逐项判断】

功能完整性：
  [ ] 每个模块的核心功能是否正常实现
  [ ] 模块间接口是否一致，数据能否正确流转
  [ ] 整体功能是否满足原始需求

代码质量：
  [ ] 无语法错误，可直接运行
  [ ] 无未处理的异常 / 边界情况
  [ ] 命名规范一致，无明显命名冲突
  [ ] 复杂度合理（单个函数不超过 50 行）

架构合理性：
  [ ] 模块划分清晰，职责单一
  [ ] 无循环依赖
  [ ] 可扩展性（未来加功能不需要大改现有模块）

【评分规则】
- 全部通过 = PASS，交付
- 通过 ≥ 80% = REWORK，指出不通过项 + 改进建议，打回对应子 Agent
- 通过 < 80% = FAIL，退回主 Agent 重新拆解

【输出格式】
逐项列出 ✅/❌，然后：
- 总体评分：X/Y 项通过
- 不通过项的具体问题（精确到模块和行号级）
- 改进建议
- 最终裁决：PASS / REWORK / FAIL

⚠️ 你是来找茬的，不是来夸的。
如果代码看起来像"能用但不专业"，那就是 REWORK。
如果核心功能缺失或架构混乱，那就是 FAIL。
```

**6A 约束叠加**：
- 评委只看交付物本身，不看子 Agent 的自验收（防互确认）。
- 须查反指标（6A.md 阶段6）：功能 100% 但 TODO>0、测试全过但空断言>0、接口文档与实际不符——计入 REWORK。
- 验收须触碰外部锚点：`exit 0`/编译通过（物理验证锚）、`git cat-file`/`diff --stat`（Git 引用完整性锚），禁止仅凭子 Agent 自述。
- 可信度标注缺失计入不通过项。

## 二、循环控制指令

```
【Gauntlet Loop 总控规则】

1. 主 Agent 拆解 → 阶段4 确认 → 子 Agent 并行执行
2. 每个子 Agent 完成后，评委 Agent 验收
3. 验收结果处理：
   - PASS → 合并到最终交付物
   - REWORK → 打回对应子 Agent，附问题清单，最多 3 次
   - FAIL → 退回主 Agent 重新拆解该模块
4. 所有模块 PASS 后，主 Agent 负责最终集成
5. 集成后再次评审：评委 Agent 对整体交付物做终审
6. 终审 PASS → 交付 / 终审 REWORK → 打回相应模块

【循环终止条件】
- 所有模块通过验收 + 整体终审通过 = 停止循环，交付
- 同一模块连续 3 次 REWORK 未通过 = 主 Agent 介入重拆或降级方案
- 总迭代次数超过 10 次 = 人工介入决策

【/loop 指令】
当你说 /loop 时：
- 重新执行最近一次未通过的验收流程
- 不要跳过任何环节
- 每次循环必须有明确的改进方向

【/rerun <module_id>】
当你说 /rerun M1 时：
- 只重新执行 M1 模块
- 其他已 PASS 模块不受影响
```

## 三、验收清单模板（可复用）

### 功能验收（必填）
```
[ ] 核心功能 A：{{功能描述}} —— 预期行为：{{预期结果}}
[ ] 核心功能 B：{{功能描述}} —— 预期行为：{{预期结果}}
[ ] 边界情况：{{边界场景}} —— 预期行为：{{预期结果}}
```

### 代码质量验收（必填）
```
[ ] 代码可运行（无语法错误 / 编译通过）
[ ] 无未处理异常
[ ] 命名规范一致
[ ] 每个函数/组件职责单一
[ ] 错误处理覆盖关键路径
```

### 架构验收（必填）
```
[ ] 模块划分清晰，高内聚低耦合
[ ] 无循环依赖
[ ] 接口定义明确，契约一致
[ ] 配置/常量与业务逻辑分离
```

### 性能验收（视任务需要）
```
[ ] 核心操作响应时间 < {{阈值}}ms
[ ] 内存无泄漏
[ ] 无阻塞主线程的同步操作
```

## 四、降级方案（平台不支持子 Agent 分发）

```
【单 Agent 迭代模式】

1. 主 Agent 拆解（同 Stage 1）
2. 逐个执行模块（M1 → M2 → M3...），每完成一个模块：
   a. 用评委提示词自检（角色切换为评委，不看自己作为执行者的自验收）
   b. 不通过就原地改进，通过后再进入下一个
3. 所有模块完成后，用评委提示词做整体终审
4. 终审不通过，定位问题模块，单独重做

/loop 直到所有模块通过验收。
```

## 五、与 KIMI K3 迭代模式对比

| 维度 | Gauntlet Loop | KIMI K3 迭代 |
|---|---|---|
| 执行方式 | 并行（子 Agent）| 串行（V1→V6）|
| 质量门 | 独立评委 Agent 盲测 | 自验收 + 用户反馈 |
| 适用场景 | 模块边界清晰的任务 | 端到端体验打磨 |
| 模型要求 | 支持子 Agent 分发 | 单 Agent 即可 |
| 速度 | 并行更快 | 串行较慢 |
| 质量上限 | 更高（评委纠偏）| 依赖用户反馈质量 |

**推荐组合**：先用 Gauntlet Loop 做模块级开发，再用 KIMI K3 迭代模式做体验打磨。
