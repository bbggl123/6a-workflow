# 第五章：六阶段主流程（静态骨架 · 内嵌动态微循环）

> 本文件是 6A 权威协议的分章加载单元。每进入一个阶段时加载对应小节即可，不必一次性全量读入。

## 架构哲学

参考 Sydney Runkle & Yuvraj Singh 的共识：
- **外层六阶段是静态图（Static Graph）**：编译期显式声明的控制流，刚性、安全、可预测。这是合规边界，不可跳过、不可动态重组。
- **每个阶段内部允许动态微循环（Dynamic Inner Loop）**：步骤级 retry、条件分支、信息补全循环。这是效率来源，在静态框架内自主运转。
- **动态图的可靠性依赖静态外壳**——外层六阶段不变，内层按需重试/补全。

## 自由度档位（v4.2 新增 · 按风险配置自由度）

> 避免关键流程失控，也避免创作任务过度僵化。各阶段不是同等严格，按单步骤风险配置自由度档位：

| 阶段 | 自由度 | 含义 |
|---|---|---|
| 阶段1 Align / 阶段2 Architect | **中** | 框架内可发挥：澄清策略、设计方案可在门控内自由探索，但产出契约与验收标准不可省 |
| 阶段3 Atomize | **低** | 拆解必须可执行、有验收标准，不得"自由发挥"留下模糊任务 |
| 阶段5 Automate 编码 | **中** | 实现方式可发挥；涉及删除 / 迁移 / 部署 → **低自由度 + 人工确认** |
| 阶段6 Assess | **高** | 鼓励挑刺，验收要苛刻，不被"已完成"叙事带跑 |

> 低自由度步骤须严格按契约执行，不得"灵活变通"；高自由度步骤允许模型自主选择验收角度与挑刺深度。

## 阶段1：Align（对齐阶段）—— 模糊需求 → 精确规范

**目标**：彻底搞清楚要做什么，杜绝"我以为你要…"

0. **部署记忆系统 + 加载 Constitution（v4 新增 · 第一步）**：
   - **trivial 任务跳过本步**（见 6A.md 第二章 triage）；standard / complex 须先过确认门槛再部署。
   - 检查项目根是否存在 `.6a-memory/` 目录
   - 若不存在：创建完整记忆目录结构（见 `references/6A-memory.md` 7.9.2），初始化 INDEX.md、session 日志、progress 文件
   - 若存在：读取 INDEX.md → current-phase.md → 最近 session 日志，恢复上下文
   - 在 session 日志中记录 `[CHECKPOINT] 6A 工作流激活`，记录当前时间、任务名称
   - 将 `.6a-memory/` 加入 `.gitignore`（如尚未加入）
   - **加载 Constitution（v4.3 新增）**：读取项目根 `CONSTITUTION.md`（若无，从 `project-skeleton/CONSTITUTION.md` 复制并按项目填充）。Constitution 是全流程冻结约束源——后续所有阶段产出门控均须校验是否违背 Constitution。在 session 日志记录 `[LOAD] CONSTITUTION.md 已加载`。
1. **项目上下文分析**：结构、技术栈、架构模式、依赖、代码风格、命名规范、已有组件、业务领域、核心数据模型、已有类似实现。**读取后立即同步到 `context/codebase.md` 等记忆文件**。
2. **前置信息筛查**：执行 4.1 第一道闸门（见 `references/6A-gatekeeper.md`）。
3. **Clarify 主动提问子阶段（v4.3 新增 · AI 主动把没搞懂的问出来）**：
   > Spec Kit 的 clarify 命令强调：AI 读完需求后**主动列出未明确的边界 / 约束 / 异常处理**，以提问清单交用户，而非靠猜。6A 此前靠用户主动补 + 阶段4 确认，缺一个 AI 主动提问的专门环节。
   - AI 基于步骤1–2 的上下文与需求，主动产出 **Clarify 提问清单** → `docs/任务名/CLARIFY_[任务名].md`，逐条列出：
     - 未明确的需求边界（做 / 不做的灰色地带）
     - 未明确的约束（性能 / 容量 / 兼容性 / 权限 / 数据格式）
     - 未明确的异常处理与降级策略
     - 未明确的外部依赖与集成假设
   - **与可信度标注联动**：前置信息筛查中可信度 <80% 的项**必须**进 Clarify 清单（<60% 的项还须标红，禁止在澄清前直接推进）。
   - Clarify 清单交用户回答；用户回答后更新到 ALIGNMENT 歧义清单与 CONSENSUS 假设确认。**未回答的 Clarify 项不得靠猜推进**——要么标为风险项，要么在阶段4 由人工拍板。
4. **输出契约（v4.2 新增 · 先于需求反推；v4.3 强化 WHAT-only 纪律）**：先定义交付物组成、每部分格式与质量标准、禁止出现的内容，再反推需要哪些输入。输出契约写入 `docs/任务名/CONTRACT_[任务名].md`，作为后续阶段的验收基线。
   - **WHAT-only 门控（v4.3 新增）**：输出契约与 ALIGNMENT/CONSENSUS 产出物**不得包含实现技术选型**（框架 / 库 / 中间件选型），技术栈讨论留到阶段2 Architect。Align 只谈「交付什么、验收什么」，不谈「用什么技术做」。违→门控不通过。
5. **需求澄清文档** → `docs/任务名/ALIGNMENT_[任务名].md`：原始需求原文、边界确认（做/不做）、我的理解、歧义清单（按优先级，吸收 Clarify 清单中未决项）、信息完整度清单。
6. **智能决策策略**：自动识别歧义；可确定问题自行回答；产品决策/技术选型/核心规则不确定时主动中断并列出问题清单。
7. **诱导提问拦截**：执行 4.3。
8. **最终共识文档** → `docs/任务名/CONSENSUS_[任务名].md`：清晰需求描述、功能范围边界（In/Out of Scope）、可测试验收标准、技术约束与集成方案、关键假设确认、每条关键假设必附 4.2 四行说明。

**质量门控（跳出条件）**：
- [ ] 需求边界清晰无歧义
- [ ] **Clarify 提问清单已产出且逐条处理（已答 / 已标风险 / 已转阶段4 拍板）**（v4.3 新增）
- [ ] 输出契约已定义（交付物组成 / 格式 / 质量标准 / 禁止项）
- [ ] **输出契约与产出物未含实现技术选型（WHAT-only）**（v4.3 新增）
- [ ] 技术方案与现有架构对齐
- [ ] 验收标准具体可量化可测试
- [ ] 关键决策点已确认
- [ ] 缺失信息已补齐或标注为风险项
- [ ] **产出未违背 CONSTITUTION.md**（v4.3 新增）
- [ ] **可信度标注完整率 100%**
- [ ] **记忆系统已部署且本阶段记忆条目完整（v4 新增）**

- ✅ 全部通过 → 进入阶段2。
- ❌ 任一不通过 → **循环回退至本阶段步骤4重做**（WHAT-only 违规回退至步骤4；Clarify 未决回退至步骤3）。

## 阶段2：Architect（架构阶段）—— 共识 → 系统设计

**目标**：先设计后编码，告别边写边想。

基于 CONSENSUS 生成 `docs/任务名/DESIGN_[任务名].md`：

1. 整体架构图（Mermaid）
2. 分层设计与核心组件职责
3. 模块依赖关系图
4. 核心接口契约（输入/输出/异常）
5. 数据流向图
6. 关键数据结构
7. 异常处理策略
8. 性能与安全考虑
9. **设计依据可信度标注（强制）**：每个核心设计决策必附 4.2 四行说明

**设计原则**：范围不过度设计；与现有架构风格一致；最大化复用；可扩展但不抽象过度；推测性设计显式标注。

**质量门控（跳出条件）**：
- [ ] 架构图清晰完整
- [ ] 接口完整无遗漏
- [ ] 与现有系统无冲突
- [ ] 方案可落地可验证
- [ ] **可信度标注完整率 100%**（架构选型、接口契约、数据结构、异常策略均附四行说明）
- [ ] **本阶段设计决策已同步到 decisions/ 记忆（v4 新增）**

- ✅ 通过 → 进入阶段3。
- ❌ 未附项视为设计未完成 → **循环回退至步骤9补标重审**。

## 阶段3：Atomize（原子化阶段）—— 大任务 → 可执行子任务

**目标**：拆到 AI 不可能做错的粒度。

基于 DESIGN 生成 `docs/任务名/TASK_[任务名].md`，每个原子任务含：
- 编号与名称
- 输入契约（前置依赖、输入数据、环境准备）
- 输出契约（交付物、验收标准）
- 实现约束（技术栈、接口规范、质量要求）
- **并行性标注（v4.3 新增 · 显式列）**：每任务必标其一——`可并行`（无前置依赖，可立即与同类任务并行派发）或 `依赖前置 [Txx]`（须等指定任务完成）。这是 Spec Kit tasks 命令「标注哪些可并行」的落地，与 Gauntlet Loop 子任务派发直接衔接：标「可并行」的任务可同时派给多个子 Agent，标「依赖前置」的任务按序串行。
- **协作模式标注（v4.4 新增 · 显式列）**：每任务/任务组必标协作模式——① 路由 ② 专家会诊 ③ 圆桌讨论 ④ 并行 ⑤ 投票 ⑥ 接力 ⑦ 生产评审 ⑧ 红蓝对抗。队长按 `references/6A-squad.md` 10.2 决策树选择。trivial 任务无需标注（队长直接处理）；standard 标模式名；complex 标模式名+派发对象。模式可在后续阶段切换（跨阶段切换规则见 `references/6A-squad.md` 10.4）。
- 依赖关系（先后/可并行，与并行性标注一致）
- 预估复杂度
- 信息依赖标注（缺失触发暂停）
- **可信度标注（强制）**：该任务能否顺利执行的确定性四行说明，外部依赖/第三方 API/未验证库版本必附

**拆分原则**：单任务 ≤200 行；按功能模块拆分；原子且独立；可独立编译/测试/验证；依赖无循环。

> **Checklist 显式化（v4.2 新增）**：原子任务清单以 `[ ]` 打勾形式产出，逐条记完成状态（>3 步必须 Checklist），便于阶段5 逐项勾选与阶段6 验收比对。
>
> **并行标注纪律（v4.3 新增）**：标注「可并行」不等于自动并行——清单不会自己派发，须由主 Agent 在阶段5 显式派发子任务 / 启动子 Agent（见 Gotchas #12）。`on-task-complete` Hook 会在前置任务完成时提醒派发后续可并行任务。

最后生成 Mermaid 任务依赖图（节点标注可并行 / 依赖前置）。

**质量门控（跳出条件）**：
- [ ] 任务 100% 覆盖需求
- [ ] 依赖无循环无死锁
- [ ] 每任务有明确可验证验收标准
- [ ] **每任务已显式标注「可并行 / 依赖前置 [Txx]」**（v4.3 新增）
- [ ] **standard/complex 任务每任务/任务组已标注协作模式**（v4.4 新增）
- [ ] 复杂度合理无巨型任务
- [ ] **可信度标注完整率 100%**
- [ ] **任务清单已同步到 progress/ 记忆（v4 新增）**

- ✅ 通过 → 进入阶段4。
- ❌ 不通过 → **循环回退至拆分步骤重做**。

## 阶段4：Approve（审批阶段）—— 人工审查确认（HITL 锚点）

**目标**：方案确认后再动手，避免做无用功。

向我展示检查清单请审批：
- [ ] 完整性 / 一致性 / 可行性 / 可控性 / 可测性 / 信息真实性
- [ ] **可信度标注完整性**

**分级交还决策权（人机分工三级制，与 4.2 阈值联动）**：

| 级别 | 触发条件 | 行动 |
|---|---|---|
| **一级** | 可信度 <60% 或信息不足 | 提醒补材料再继续，不强行推进 |
| **二级** | 长篇逻辑冲突 / 用户诱导造假 / 设计矛盾 / 可信度 60%–80% | 直接停止生成，等待人工审核 |
| **三级** | 金融/法务/政务/医疗等高风险领域，或可信度 <80% 的高风险结论 | AI 仅提供参考素材，最终结论须人工确认签字 |

等待我明确回复"确认"或"可以开始"后进入阶段5；有修改则迭代更新前三阶段文档。
**跳出条件**：收到明确"确认"指令方跳出本阶段；否则停留等待。

> **此阶段是整张图中最重要的 Grounding Anchor 之一**——人类判断是不可被 AI 替代的外部锚点。

## 阶段5：Automate（自动化执行）—— 按文档编码实现（Inner Loop 所在地）

**目标**：按计划执行，有据可查。

> 此阶段是 **动态内核** 所在地——在外层静态骨架约束下，内部允许灵活的执行微循环。

> **协作模式派发（v4.4 新增）**：进入阶段5 前，队长按 TASK 文档中标注的协作模式派发任务。8 种模式的派发模板与操作协议见 `project-skeleton/workflows/squad-modes.md`。派发时在 session 日志记录 `[DECISION] 协作模式：{模式名}，理由：{一句话}`。平台不支持子 Agent 分发时按 `references/6A-squad.md` 10.6 降级为单 Agent 模拟。Gauntlet Loop 仍是 complex 任务并行+评审的推荐预设组合。

1. 严格按 TASK 依赖顺序逐任务执行。
2. 创建 `docs/任务名/ACCEPTANCE_[任务名].md` 记录完成情况。
3. **每子任务 Inner Loop**（五步微循环 + 记忆同步）：
   - ① 执行前检查（输入契约/环境/依赖）→ 记录 `[CHECKPOINT] 开始任务 Txx` 到 session
   - ② 实现核心逻辑（严格按 DESIGN）→ 每修改一个文件记录 `[MODIFY]`
   - ③ 编写单元测试（正常/边界/异常）→ 记录 `[MODIFY]` 测试文件
   - ④ 运行验证（测试通过、功能正常）→ 记录 `[RUN]` 命令和结果
   - ⑤ 同步更新文档 → 标记完成 → 记录 `[CHECKPOINT] 任务 Txx 完成`
   - **`on-task-complete` Hook 触发（v4.3 新增 · 任务粒度检查点）**：单任务 Txx 标记完成时触发，固定动作：⑴ 校验该任务交付物 vs TASK 契约（实质产出是否存在：文件改动 / 测试 / 验证结果）；⑵ 在 progress/ 勾选 `[ ]`→`[x]` 并刷新任务清单状态；⑶ 检测「制造干活的假象」——留痕密集但无实质产出即判不通过，打回重做；⑷ 若该任务为后续「可并行」任务的前置，提醒主 Agent 派发后续任务。详见 `references/6A-hooks.md`。这是对 v4.2 `on-phase-exit`（阶段粒度）的细化——任务粒度的检查点防止单任务「假完成」混过阶段门控。
   - **记忆同步（v4 新增）**：上述每一步完成后，立即同步到 `.6a-memory/session/` 和 `progress/`，不要等任务结束再补记
4. **长内容分段自检**：执行 4.4。
5. 代码质量：遵循规范、风格一致、复用现有组件、简洁有注释、敏感信息走 `.env`。
6. 异常处理：遇不确定立即中断，记录于 TASK 文档，寻求人工澄清。
7. **全程留痕**：执行 4.5。

**循环逻辑（Inner Loop 退出条件）**：
- 单任务 ③④ 不通过 → **微循环回退至 ① 重做**（最多 3 轮）
- 连续 3 轮失败或遇不确定 → **触发阶段4 二级回环，交人工**
- 整体进度停滞（无进展检测）→ **触发预算/时间审查，考虑降级方案**

> 执行层治理升级见 `references/6A-engineering.md` 7.3：本阶段产出须以 PR/分支提交，经门禁脚本通过后合入。

## 阶段6：Assess（评估阶段）—— 质量验收交付（审计环所在地）

**目标**：不合格就重来，确保交付质量。

> 此阶段承载 **审计环（Audit Loop）** 职责——不仅检查当前交付物质量，还要验证整个流程没有被"刷指标"。

1. **整体验收**（更新至 ACCEPTANCE）：
   - [ ] 需求 100% 实现
   - [ ] 验收标准全满足
   - [ ] 编译无报错无警告
   - [ ] 测试用例全通过
   - [ ] 功能完整
   - [ ] 实现与设计一致
   - [ ] 未破坏现有功能
   - [ ] **幻觉自查通过**（无编造数据/虚构依赖/前后矛盾）
   - [ ] **可信度标注完整率 100%**
   - [ ] **记忆系统完整：session/decisions/progress 均已同步，lessons 已沉淀（v4 新增）**

2. **反指标检查（Anti-Goodhart Audit）（防「指标被刷」）**：

   > 参考古德哈特定律：**当一个指标变成目标时，它就不再是一个好指标。** 单一优化环会自发学会"刷分"。评估 Agent 必须主动检查以下反指标：

   | 主指标 | 反指标（Counter-Metric） | 告警条件 |
   |---|---|---|
   | 功能完成率 | 代码质量（TODO 占位率、硬编码数、异常处理覆盖率） | 功能 100% 但 TODO > 0 或硬编码 > N |
   | 测试通过率 | 测试有效性（断言是否有实质校验、是否只 assert True） | 通过率 100% 但空断言 > 0 |
   | 交付速度 | 可追溯性（LOG 编号连续性、TRACE 完整度） | 速度快但留痕缺失 |
   | 文档完整度 | 文档与代码一致性（接口文档是否与实际匹配） | 文档齐全但与实际不符 |

   > 反指标可由确定性脚本计算：`scripts/anti-metric.sh` 算 TODO 占位率、断言有效性比值，评估 Agent 据脚本结果判断。

3. **质量评估维度**：代码 / 测试 / 文档 / 集成 / 债务 / 诚实度 / **标注合规度 / 反指标健康度**

4. **最终交付物**：
   - `docs/任务名/FINAL_[任务名].md`：项目总结
   - `docs/任务名/TODO_[任务名].md`：待办、遗留、优化建议
