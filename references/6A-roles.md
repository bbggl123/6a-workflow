# 第三章：角色与职责拆分（明确职责，拆分边界）

> 本文件是 6A 权威协议的分章加载单元。规划阶段开始时加载。

即使在同一会话内，也按以下四个清晰、不重叠的角色执行：

| 角色 | 职责 | 红线 |
|---|---|---|
| **规划 Agent** | 阶段1–4：对齐、设计、拆解、产出待审批方案；**v4.4 新增：阶段3 拆解后为每个任务/任务组选择协作模式（8 种智能小队模式）并记录在 TASK 文档，阶段5 前按模式派发** | 不得写实现代码；不得替用户做产品/选型最终决策；不得跳过模式选择（standard/complex 任务） |
| **执行 Agent** | 阶段5：按 TASK 文档逐任务编码与单测 | 不得偏离 DESIGN/TASK 文档；不得用 TODO 占位掩盖未实现 |
| **评估 Agent** | 阶段6：验收、质量评估、交付物与留痕汇总 | 不得放宽验收标准；发现幻觉必须打回重做 |
| **守门员 Agent（跨阶段）** | 全程防幻觉筛查与可信度标注强制校验 | 任一阶段可信度标注缺失/失真，直接判定该阶段不合格 |
| **评委 Agent（Gauntlet Loop 模式 · v4.1 新增）** | 阶段5 并行执行后的独立盲测验收：逐项清单验收、不达标打回、终审 | 不得放宽验收标准；不得看子 Agent 的自验收，只看交付物本身；"能用但不专业"即判 REWORK |

> **单 Agent 会话中以"角色切换"模拟多 Agent 即可，但职责边界必须显式声明、不可混用。**
>
> **Gauntlet Loop 角色映射**：主 Agent（拆解 & 编排 & 集成）= 规划 Agent；子 Agent（并行执行模块）= 多个执行 Agent 实例；评委 Agent（盲测验收）= 评估 Agent 的独立盲测变体 + 守门员的可信度校验。详见 `references/6A-gauntlet.md`。
>
> **智能小队角色映射（v4.4 新增）**：队长（模式选择 + 派发 + 收口）= 规划 Agent；各模式下被派发的成员 = 执行 Agent / 评估 Agent 的角色实例；红蓝对抗的裁判 = 评估 Agent 变体；生产评审的评审者 = 评估 Agent 变体。8 种模式的详细协议见 `references/6A-squad.md`。

## 3.1 可靠性活在边上，不在节点上（核心原则）

> 引自图工程核心洞察：**The reliability lives in the EDGES, not the nodes.**

单纯保证每个角色（节点）的产出质量是不够的——**角色之间的信息传递与状态流转（边）才是腐败滋生的地方**。因此额外定义边治理规则：

| 边（Edge） | 治理规则 | 失败处理 |
|---|---|---|
| 规划 → 执行 | DESIGN/TASK 必须经 Approve 签收方可进入执行 | 未签收不得启动阶段5 |
| 执行 → 执行（并行 Worker 共享分支） | 遵守分支保护盾「消失即停」，禁止 Worker 强推 / 硬重置（见 `references/6A-git-shield.md`） | 引用异常时 Worker 停手，交 Lead 恢复 |
| 执行 → 评估 | 代码变更必须以 PR 形式提交，经 CI 门禁通过；先校验 Git 引用完整性 | 门禁不过或 HEAD 异常不可合入，回退重做 |
| 评估 → 规划（回环） | 验收不通过的反馈必须结构化（具体到任务编号+原因） | 禁止模糊打回"重做" |
| 任一角色 → 外部世界 | 所有对外输出必须附可信度标注 | 缺标注视为未完成 |

> **多 Agent 共享分支的边尤其脆弱**：当多个执行 Agent 在同一 git 分支并行提交时，"边"上的引用状态是腐败高发处（提交被环境悄悄挪回旧基线）。`references/6A-git-shield.md`「分支保护盾」是这条边的专属治理规则。
