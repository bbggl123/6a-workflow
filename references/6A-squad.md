# 第十章：智能小队协作模式（v4.4 新增）

> 本文件是 6A 权威协议的分章加载单元。当任务规模为 standard/complex、涉及多 Agent 协作或需要主 Agent 选择协作策略时加载。

## 10.0 为什么需要协作模式选择

6A 此前的多 Agent 协作只有 Gauntlet Loop 一种（第九章，并行执行 + 评委盲测）。但真实项目中，不同任务、不同阶段需要不同的协作策略——路由分诊适合领域明确的任务，圆桌讨论适合有分歧的设计决策，接力模式适合串行流水线，红蓝对抗适合安全审计。**单一模式不可能适配所有场景**。

v4.4 引入 **智能小队** 框架：主 Agent（队长）在阶段3 Atomize 拆解任务后、阶段5 Automate 执行前，根据任务特征**自动选择最合适的协作模式**派发工作；且允许**同一任务的不同阶段使用不同模式**——例如 Align 用路由模式找领域专家澄清需求，Automate 用并行模式分模块开发，Assess 用红蓝对抗做安全审计。

> **与 Gauntlet Loop 的关系**：Gauntlet Loop（第九章）本质是「并行模式 + 生产评审模式」的组合特例，仍然保留为 complex 任务的推荐执行策略。本章定义的 8 种模式是**通用协作框架**，Gauntlet Loop 是其中一种预设组合。

## 10.1 八种协作模式总览

| 模式 | 一句话 | 核心机制 | 典型适用场景 |
|---|---|---|---|
| **① 路由模式** | 队长分诊，转交唯一最匹配专家 | @单专家就地处理并交付 | 领域明确的单一任务 |
| **② 专家会诊** | 同一问题多角度并行独立作答 | 并行子任务→队长整合 | 需求分析、风险评估需多视角 |
| **③ 圆桌讨论** | 有分歧的议题，接龙发言+追问 | @全体→轮流发言→队长收口 | 设计决策、方案选型有实质分歧 |
| **④ 并行模式** | 独立子任务并行扇出汇总 | 并行子任务→去重合并 | 模块独立的开发任务 |
| **⑤ 投票模式** | 同一问题多解择优 | 并行子任务→队长择优 | 关键算法/方案，要 best-of-N |
| **⑥ 接力模式** | 串行依赖流水线 | 依赖链子任务→自动解阻塞 | 前后端衔接、数据处理管线 |
| **⑦ 生产评审** | 产出初稿→评审→迭代 | @生产者→@评审者→循环 | 代码 review、文档评审 |
| **⑧ 红蓝对抗** | 同台对辩，队长裁判 | 红蓝直接交锋→队长裁决 | 安全审计、架构辩论、风险论证 |

## 10.2 模式选择决策树（队长在阶段3 Atomize 后执行）

> 队长（主 Agent / 规划 Agent）完成任务拆解后，**对每个任务或任务组**走以下决策树选择协作模式。决策结果写入 TASK 文档的「协作模式」列。

```
任务是否可由单一领域专家独立完成？
├─ 是 → ① 路由模式（@ 该专家就地处理）
└─ 否 → 任务是否有串行依赖（B 必须等 A 完成）？
    ├─ 是 → ⑥ 接力模式（依赖链串联）
    └─ 否 → 是否需要多个独立视角回答同一问题？
        ├─ 是 → 是否需要从中选最优解？
        │   ├─ 是 → ⑤ 投票模式（并行出解→择优）
        │   └─ 否 → 是否有实质分歧需要辩论？
        │       ├─ 是 → ③ 圆桌讨论（接龙+追问）
        │       └─ 否 → ② 专家会诊（并行独立→整合）
        └─ 否 → 任务是否可拆成独立并行子任务？
            ├─ 是 → ④ 并行模式（扇出汇总）
            └─ 否 → 是否需要产出→评审→迭代循环？
                ├─ 是 → ⑦ 生产评审（生产者↔评审者）
                └─ 否 → 是否需要对抗性辩论（安全/风险）？
                    ├─ 是 → ⑧ 红蓝对抗（红蓝对辩→裁判）
                    └─ 否 → 队长直接处理（无匹配模式）
```

### 模式选择的快速判断表

| 判断信号 | 推荐模式 |
|---|---|
| 只有一个领域专家能处理，无需协作 | ① 路由 |
| 同一问题需要法务+技术+产品三视角 | ② 专家会诊 |
| 设计方案 A vs B 有真实分歧，需充分辩论 | ③ 圆桌讨论 |
| 5 个独立模块可同时开发 | ④ 并行 |
| 同一算法要 3 种实现选最好的 | ⑤ 投票 |
| 数据清洗→特征工程→模型训练，前一步是后一步输入 | ⑥ 接力 |
| 写完代码需要资深 review 才能合入 | ⑦ 生产评审 |
| 安全方案要攻防双方对抗验证 | ⑧ 红蓝对抗 |

## 10.3 各模式详细协议

### ① 路由模式（路由分诊）

**适用**：任务命中唯一最匹配的领域专家，无需多人协作。

**流程**：
1. 队长接收任务，判断其类型/领域。
2. 命中唯一最匹配者，在本任务内 @ 该专家请其接手。
3. 只 @ 一位专家时，派发时告知对方「交付后自己结束任务、无需回传」；该专家就地处理并直接交付，其交付即最终答案，队长不再复述或总结。
4. @ 多位专家时（多个独立领域任务），各自完成后回传队长，由队长汇总收口。
5. 无匹配时由队长直接处理。

**6A 落点**：Align 阶段路由给领域专家澄清需求；Assess 阶段路由给安全/性能专家做专项验收。

**门控**：被路由的专家交付物仍须过可信度标注 + Constitution 校验。

### ② 专家会诊模式

**适用**：同一问题需要多个专业角度的独立分析，各方互不影响。

**流程**：
1. 队长就同一问题，按不同专业角度拆成多个相互独立的并行子任务，各专家在隔离上下文中独立作答、互不影响：
   - 子任务 → {专家A}：从 ___ 角度
   - 子任务 → {专家B}：从 ___ 角度
2. 全部子任务完成后队长被唤醒，整合各方意见形成统一结论并交付。

**6A 落点**：Align 阶段多视角需求分析（产品+技术+法务）；Assess 阶段多维度质量评估。

**门控**：各方独立作答期间不得互相参考；整合时须标注分歧点与整合依据。

### ③ 圆桌讨论模式

**适用**：议题有实质分歧空间，需要充分讨论才能收敛。

**流程**：
1. 队长先掂量议题有无实质分歧空间：若明显没有，直接给结论或征询一位成员即可，并简短说明理由；有分歧则开圆桌。
2. 开场只发一条：贴原样议题、加一份所有成员通用的交付要求（要回答什么、要带什么依据、篇幅几何），末尾把全体成员的名字一起 @ 出来，请他们按先后接龙发言。成员轮到时自己决定从哪个角度切入，给出独立判断，可以回应他人、提新角度、被说服后改立场，不必逐条对答。发完即等回复。
3. 每轮走完，队长总结共识、分歧和还值得深挖的点，就薄弱处向相关成员追问（挑战证据不足的论点、补缺失视角）；被追问的成员正面回应：接受修正，或拿出更强的依据反驳。
4. 判断原则：共识来得越快，越要挑出最薄弱的论点点名质疑——扎实的结论是经过质疑与回应后立住的。
5. 收口，按分歧情况决定：
   - 无实质分歧 → 收敛；
   - 仍有分歧且未达 3 轮上限 → 换人打头再起一轮；
   - 达 3 轮仍未收敛 → 队长综合各方拍板，注明保留意见。

**6A 落点**：Architect 阶段架构方案辩论；Approve 阶段多方利益对齐。

**门控**：收口结论须附「结论如何达成、哪些质疑修正了判断」说明；保留意见显式标注。

### ④ 并行模式（并行扇出汇总）

**适用**：任务可拆成多个相互独立的并行子任务，彼此无依赖。

**流程**：
1. 队长将任务拆成多个相互独立的并行子任务。
2. 分别指派：子任务→{成员A}、子任务→{成员B}、子任务→{成员C}（彼此无依赖）。
3. 全部子任务完成后队长被唤醒，去重/合并汇总交付。

**6A 落点**：Automate 阶段独立模块并行开发。与 Gauntlet Loop 的区别：Gauntlet Loop 额外叠加评委盲测验收；纯并行模式由队长直接合并。

**门控**：合并时校验接口一致性、命名冲突、循环依赖。

### ⑤ 投票模式（投票择优）

**适用**：同一问题需要多个独立解，从中选最优。

**流程**：
1. 队长就同一问题拆出多个并行子任务，分派给{成员A} {成员B} {成员C}，彼此隔离、互不可见，保证独立作答。
2. 各子任务完成后队长收集答案。
3. 按多数票 / 最优解择优交付。

**6A 落点**：Automate 阶段关键算法/核心模块要 best-of-N；Architect 阶段多方案选优。

**门控**：择优须附评判标准与选择依据；落选方案保留为备选（标注差异点）。

### ⑥ 接力模式（接力流水线）

**适用**：任务有串行依赖，前一步是后一步的输入。

**流程**：
1. 队长按固定顺序拆成串行子任务，用依赖串联：
   - 子任务 → 指派{成员1}：完成 ___
   - 子任务（依赖上一步）→ 指派{成员2}：基于上游产物完成 ___
   - 子任务（依赖上一步）→ 指派{成员3}：完成 ___ 并交付
2. 每个子任务完成自动解阻塞下一个；全部完成后队长汇总。

> 若任务本身是单一不可拆分的交付物、切不出有意义的串行环节，则降级为单成员直派完成，不要硬凑棒次。

**6A 落点**：Automate 阶段数据处理管线（清洗→特征→训练→评估）；全栈开发（API→前端→集成）。

**门控**：每棒交接时校验上游产物完整性；上游不达标不交付下游。

### ⑦ 生产评审模式（生产-评审）

**适用**：需要产出初稿→评审→迭代的循环。

**流程**：
1. {生产者} 在本任务内产出初稿（队长可兼任），并 @ {评审者} 请其评审。
2. @ {评审者} 必须给出明确结论：通过 → @ {生产者} 交付；不通过 → 列具体意见。
3. 不通过则 @ {生产者} 就地修改重提，@ {评审者} 复审，循环最多 3 轮；超轮次队长兜底。

**6A 落点**：Automate→Assess 衔接（代码产出→code review→修改→复审）；文档撰写流程。

**门控**：评审者必须给出明确结论（通过/不通过+具体意见），不得模糊放行；超 3 轮触发队长兜底。

### ⑧ 红蓝对抗模式（对辩）

**适用**：需要对抗性辩论验证（安全审计、架构辩论、风险论证）。

**流程**：
1. 红蓝对抗是同台对辩：双方在同一处直接往来、看得见对方的实际主张并即时回应。队长开场点明辩题、双方立场与先后次序（红方先立论），指定两名不同成员分任红蓝（队长不下场任一方），随即退出交锋，只在最后作为裁判收口。
2. 双方立论义务对称：红方先发布己方完整主张（核心判断、论据、边界），发布后 @ 蓝方；蓝方先发布己方完整主张，再逐条挑战红方已发布的实际主张，然后 @ 红方。若轮到时对方主张尚未发布，明确说明等待，不预判、不空打。
3. 交锋过程由双方直接互相 @ 接力推进，不经过队长中转：被挑战方正面回应——接受并修正立场，或拿出更强的依据反驳——并可对对方立论发起新挑战，然后 @ 对方；没有被回应的挑战等于没有发生。
4. 当不再出现新的有效反驳时，任一方 @ 队长请求收口；交锋最多 3 个回合，超出由队长直接介入。
5. 队长收口前先确认双方最强论点都被对方正面回应过，未被回应的点名补回应；然后作为裁判权衡双方论据给出结论并交付，说明结论如何达成、哪些攻防修正了裁判最初的判断；多轮仍不收敛则拍板并注明保留意见。

**6A 落点**：Assess 阶段安全审计（红方攻/蓝方守）；Architect 阶段架构方案辩论。

**门控**：队长不下场任一方；收口结论须附「结论如何达成、哪些攻防修正了判断」说明。

## 10.4 跨阶段模式切换（核心能力）

> 同一任务的不同阶段可以使用不同协作模式。队长在每阶段开始时重新评估并选择模式。

**典型跨阶段组合**：

| 阶段 | 推荐模式 | 理由 |
|---|---|---|
| Align | ① 路由 或 ② 专家会诊 | 需求澄清需要领域专家；多视角需求分析需要会诊 |
| Architect | ③ 圆桌讨论 或 ⑧ 红蓝对抗 | 设计方案有分歧需要辩论；架构选型需要对抗验证 |
| Atomize | 队长独立完成（低自由度） | 拆解必须可执行，不发散 |
| Approve | ③ 圆桌讨论（多方利益对齐） | 多方共识需要讨论收敛 |
| Automate | ④ 并行 / ⑥ 接力 / ⑤ 投票 / Gauntlet | 独立模块并行；串行管线接力；关键算法投票；Gauntlet 综合并行+评审 |
| Assess | ⑦ 生产评审 或 ⑧ 红蓝对抗 | 代码 review 走生产评审；安全审计走红蓝对抗 |

**切换规则**：
- 队长在 TASK 文档中为每个任务/任务组标注协作模式（与并行性标注并列）。
- 模式切换不跨阶段回退——Automate 阶段切换模式不影响已完成阶段的产出。
- 模式选择记录在 session 日志 `[DECISION] 协作模式：{模式名}，理由：{一句话}`。

## 10.5 与 6A 既有机制的融合

| 6A 机制 | 在智能小队中的落点 |
|---|---|
| **可信度标注** | 所有模式中各成员的产出均附四行可信度说明；队长整合/裁决时校验标注完整性 |
| **外部锚点** | 路由/会诊/投票模式的交付物须触碰外部锚点（编译/测试/Git 引用）；红蓝对抗的论据须有外部依据 |
| **反指标环** | 并行/投票模式的合并结果须查反指标（TODO/空断言）；生产评审的「通过」不得仅凭完成率 |
| **分支保护盾** | 并行/接力/Gauntlet 模式多 Agent 共享分支时守「消失即停」 |
| **记忆系统** | 所有模式的派发、成员回复、队长裁决均同步到 `.6a-memory/session/` |
| **人机锚点** | 圆桌讨论 3 轮未收敛、红蓝对抗 3 回合未收敛、生产评审超 3 轮——均触发人工介入 |
| **Constitution** | 所有模式的产出不得违背 Constitution；红蓝对抗中违宪主张直接判负 |

## 10.6 降级方案（平台不支持子 Agent 分发时）

| 模式 | 降级策略 |
|---|---|
| ① 路由 | 队长以该专家角色视角直接处理 |
| ② 专家会诊 | 队长依次切换角色视角独立作答，最后整合 |
| ③ 圆桌讨论 | 队长模拟各方视角自我辩论，记录各方立场后裁决 |
| ④ 并行 | 队长串行执行各子任务后合并 |
| ⑤ 投票 | 队长生成多版方案后自评择优 |
| ⑥ 接力 | 队长按序执行各棒（与单 Agent 模式一致） |
| ⑦ 生产评审 | 队长先以生产者角色产出，再切换评审者角色自审 |
| ⑧ 红蓝对抗 | 队长模拟红蓝双方自我对辩，记录攻防后裁决 |

> 降级时须在 session 日志标注 `[DEGRADE] {模式名} 降级为单 Agent 模拟`，且裁决/整合结论须额外审查（单 Agent 模拟多视角的盲区更大）。
